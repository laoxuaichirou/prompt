Open




Open




























Summary

When a multi-line prompt string is passed to generate create (e.g. via --prompt "$(cat prompt.txt)"), the job is accepted and completes normally, but only the text before the first blank line is actually used by the model. There is no warning, error, or indication of truncation — the job returns status: completed with a result URL. In production this silently degraded multiple video generations before we diagnosed it.


Reproduction


Prepare a prompt file containing several paragraphs separated by blank lines (typical for structured video prompts: anchor block, camera, timed beats).


Run:




higgsfield generate create minimax_h3 --aspect_ratio 16:9 --resolution 2K --duration 15 --image-references <id> --prompt "$(cat prompt.txt)" --json





The job is accepted and completes normally.



Expected

Either the full prompt is delivered, or the CLI rejects/warns about multi-line --prompt input.


Actual

The model receives only the text up to the first blank line and behaves as if the rest of the prompt does not exist. Verified across at least four incidents (including jobs 34065870 and 8d44aef3, 2026-09-23): text after the first blank line (camera behavior, timed action beats) was demonstrably not executed, while the job completed with no error. In one measured case only ~1,100 characters of a ~6,000-character prompt were effective.


Impact

Silent, non-obvious degradation of generation quality. Structured prompts (the recommended style for timed/beat-based video prompts) are effectively unusable, and the failure looks like a model-behavior problem rather than a CLI input-handling problem, which makes it very hard to diagnose.


Suggested fix (either)


Join/normalize the prompt to a single line before submission, or


Fail fast with a clear error when --prompt contains newlines/blank lines, or


At minimum, return the effective prompt length/hash in the job payload so truncation is detectable.
